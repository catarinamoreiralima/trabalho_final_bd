\section{Introdução}

Este trabalho apresenta o desenvolvimento de um protótipo de aplicação completa para exploração da base de dados da Fórmula 1 integrada a dados geográficos de cidades, países e aeroportos.

A aplicação permite autenticar usuários com perfis distintos, apresentar \textit{dashboards} personalizados, executar relatórios e realizar operações de cadastro conforme as permissões de cada tipo de usuário.

\section{Preparação da Base de Dados}

A base utilizada foi preparada a partir dos \textit{scripts} desenvolvidos ao longo da disciplina. A execução foi organizada na seguinte ordem:

\begin{enumerate}
    \item \texttt{create\_table.sql}: criação do esquema relacional;
    \item \texttt{insert\_table.sql}: carga dos arquivos CSV e TSV;
    \item \texttt{clean\_data.sql}: normalização, deduplicação e ajuste de vínculos entre as tabelas;
    \item \texttt{app\_users.sql}: usuários, autenticação, auditoria e triggers;
    \item \texttt{app\_actions.sql}: ações de cadastro e consulta por perfil;
    \item \texttt{app\_indexes.sql}: índices auxiliares;
    \item \texttt{app\_views.sql}: views reutilizáveis pela aplicação;
    \item \texttt{app\_dashboard.sql}: funções de \textit{dashboard};
    \item \texttt{app\_reports.sql}: funções de relatórios.
\end{enumerate}

\subsection{Execução com Docker}

Para facilitar a reprodução do ambiente entre os membros do grupo, foi utilizado Docker com PostgreSQL. A carga foi separada em dois scripts: um para a base de dados e outro para a camada da aplicação.

\begin{lstlisting}[style=sqlstyle]
./scripts/load_database.sh
./scripts/load_app.sh
\end{lstlisting}

O script \texttt{load\_database.sh} executa a criação do esquema, a carga dos dados e a limpeza. O script \texttt{load\_app.sh} executa os arquivos de usuários, ações, índices, views, dashboards e relatórios. Assim, durante o desenvolvimento de novas funções, é possível recarregar apenas a camada da aplicação.

Os dados de conexão utilizados foram:

\begin{itemize}
    \item Banco: \texttt{f1db}
    \item Usuário: \texttt{f1user}
    \item Porta: \texttt{5433}
\end{itemize}

\section{Views Reutilizáveis}

Foi criado o arquivo \texttt{app\_views.sql} para concentrar consultas reutilizáveis pela aplicação. A view \texttt{vw\_resultados\_corridas} reúne os dados de resultados de corrida com temporada, piloto, escuderia, status e circuito.

Essa view centraliza junções frequentes entre as tabelas \texttt{results}, \texttt{races}, \texttt{seasons}, \texttt{drivers}, \texttt{constructors}, \texttt{status} e \texttt{circuits}. Com isso, as funções de \textit{dashboard} e de relatórios ficam mais simples e reutilizam a mesma base lógica. Os filtros específicos continuam sendo aplicados nas funções, de acordo com o perfil do usuário logado, como administrador, escuderia ou piloto.

Também foi criada a view \texttt{vw\_aeroportos\_cidades\_paises}, que reúne aeroportos, cidades, países e tipos de aeroporto. Essa view é utilizada no relatório de aeroportos próximos a uma cidade brasileira, mantendo na função apenas o filtro pela cidade informada e o cálculo da distância geográfica.

A view \texttt{vw\_corridas\_resumo} resume cada corrida com ano, rodada, circuito, voltas registradas e quantidade de pilotos participantes. Ela é usada no relatório hierárquico de corridas do administrador, evitando repetir a agregação dentro da função de relatório.

A view \texttt{vw\_escuderia\_pilotos} reúne escuderias, pilotos, países e a origem do vínculo entre escuderia e piloto. Essa view é construída sobre a tabela \texttt{app\_escuderia\_pilotos}, que combina vínculos históricos inferidos de \texttt{results} com vínculos criados pela importação de pilotos por arquivo.

\section{Modelo de Usuários e Autenticação}

A aplicação possui três tipos de usuários, cada um com permissões e visões distintas:

\begin{itemize}
    \item \textbf{Admin}: usuário administrador do sistema;
    \item \textbf{Escuderia}: usuário associado a uma escuderia;
    \item \textbf{Piloto}: usuário associado a um piloto.
\end{itemize}

Foi criada a tabela \texttt{users}, contendo os atributos \texttt{userid}, \texttt{login}, \texttt{password}, \texttt{tipo} e \texttt{id\_original}. O atributo \texttt{id\_original} referencia o identificador original de piloto ou escuderia, conforme o tipo de usuário.

\subsection{Proteção das Senhas}

A autenticação foi implementada diretamente pela tabela \texttt{users}. Por isso, as senhas não são armazenadas em texto puro. Foi utilizada a extensão \texttt{pgcrypto}, com as funções \texttt{crypt()} e \texttt{gen\_salt()}. A função \texttt{app\_alterar\_senha} permite trocar a senha validando a senha atual do usuário.

\begin{lstlisting}[style=sqlstyle]
CREATE OR REPLACE FUNCTION app_hash_password(p_plain_password TEXT)
RETURNS TEXT AS $$
BEGIN
    RETURN crypt(p_plain_password, gen_salt('bf'));
END;
$$ LANGUAGE plpgsql;
\end{lstlisting}

\subsection{Auditoria de Acesso}

Foi criada a tabela \texttt{users\_log}, responsável por registrar eventos de \texttt{LOGIN} e \texttt{LOGOUT}. A função \texttt{app\_login} registra automaticamente a entrada do usuário quando a autenticação é realizada com sucesso.

\section{Triggers Implementadas}

\subsection{Sincronização de Pilotos com Usuários}
A trigger associada à tabela \texttt{drivers} cria automaticamente um usuário do tipo \texttt{Piloto} sempre que um novo piloto é cadastrado. Em atualizações, a trigger ajusta o login quando necessário, mas preserva a senha já alterada pelo usuário.

\subsection{Remoção de Usuários de Pilotos}

Também foi criada uma trigger associada à tabela \texttt{drivers} para remover automaticamente o usuário do tipo \texttt{Piloto} quando o piloto correspondente é removido. Antes da remoção do usuário, os registros relacionados em \texttt{users\_log} são apagados para respeitar a chave estrangeira existente entre \texttt{users\_log} e \texttt{users}.

\subsection{Sincronização de Escuderias com Usuários}

A trigger associada à tabela \texttt{constructors} cria automaticamente um usuário do tipo \texttt{Escuderia} sempre que uma nova escuderia é cadastrada. Em atualizações, a trigger ajusta o login quando necessário, mas preserva a senha já alterada pelo usuário.

\subsection{Remoção de Usuários de Escuderias}

Foi criada uma trigger associada à tabela \texttt{constructors} para remover automaticamente o usuário do tipo \texttt{Escuderia} quando a escuderia correspondente é removida. Assim como no caso dos pilotos, os registros associados em \texttt{users\_log} são removidos antes da exclusão do usuário.

\subsection{Atualização de Data em Usuários}

A trigger de atualização da tabela \texttt{users} atualiza automaticamente o campo \texttt{updated\_at} quando uma tupla é modificada.

\subsection{Sincronização de Vínculos entre Escuderias e Pilotos}

A trigger associada à tabela \texttt{results} mantém a tabela \texttt{app\_escuderia\_pilotos} atualizada quando novos resultados criam vínculos entre pilotos e escuderias. Essa estrutura aceita que um mesmo piloto esteja vinculado a mais de uma escuderia, preservando mudanças de escuderia e histórico de carreira.

\section{Ações Implementadas}

Foram criadas funções auxiliares para representar ações solicitadas na especificação:

\begin{itemize}
    \item \texttt{app\_admin\_cadastrar\_escuderia}: cadastra uma nova escuderia e deixa a criação do usuário correspondente a cargo da trigger;
    \item \texttt{app\_admin\_cadastrar\_piloto}: cadastra um novo piloto e deixa a criação do usuário correspondente a cargo da trigger;
    \item \texttt{app\_escuderia\_processar\_importacao\_pilotos}: processa linhas carregadas por arquivo em uma tabela de apoio, cadastrando pilotos novos e criando vínculos com a escuderia;
    \item \texttt{app\_escuderia\_listar\_pilotos}: lista os pilotos vinculados à escuderia no cadastro da aplicação;
    \item \texttt{app\_escuderia\_consultar\_piloto\_por\_sobrenome}: consulta pilotos pelo sobrenome que \emph{já correram} pela escuderia logada, consultando diretamente a tabela \texttt{results}, conforme a dica do enunciado.
\end{itemize}

Para suportar a importação de pilotos por escuderia, foi criada uma tabela própria de vínculo entre escuderias e pilotos. A relação original entre piloto e escuderia aparece apenas em \texttt{results}; portanto, pilotos recém-importados ainda não teriam vínculo visível caso a aplicação dependesse somente dos resultados históricos. Por isso, a tabela é inicialmente populada com pares distintos de \texttt{results}, recebe vínculos criados por importação de arquivo e é atualizada por trigger quando novos resultados são registrados.

Após a revisão das funções, foi mantida a separação entre consultas de desempenho e consultas cadastrais. Dashboards e relatórios que calculam pontos, vitórias, temporadas, corridas ou status usam \texttt{results} ou \texttt{vw\_resultados\_corridas}, pois dependem de participação real em corridas. A consulta de piloto por sobrenome também se baseia em \texttt{results}, pois o enunciado pede pilotos que \emph{já correram} pela escuderia. Já a \emph{listagem} cadastral de pilotos vinculados à escuderia (\texttt{app\_escuderia\_listar\_pilotos}) usa \texttt{app\_escuderia\_pilotos} ou \texttt{vw\_escuderia\_pilotos}, pois nesse caso faz sentido incluir também pilotos importados por arquivo, mesmo antes de existirem resultados para eles.

\section{Relatórios}

\subsection{Relatório 1 -- Admin: Resultados por Status}

Este relatório apresenta a quantidade de resultados agrupados por status de corrida.

\subsection{Relatório 2 -- Admin: Aeroportos Próximos a Cidade Brasileira}

Este relatório recebe o nome de uma cidade e retorna aeroportos brasileiros dos tipos \texttt{medium\_airport} e \texttt{large\_airport} localizados a até 100 km da cidade pesquisada. Os dados de aeroporto são obtidos pela view \texttt{vw\_aeroportos\_cidades\_paises}.

Para o cálculo de distância foi utilizada a extensão \texttt{earthdistance}, juntamente com \texttt{cube}.

\begin{lstlisting}[style=sqlstyle]
earth_distance(
    ll_to_earth(c.latitude, c.longitude),
    ll_to_earth(vap.latitude_aeroporto, vap.longitude_aeroporto)
) / 1000.0
\end{lstlisting}

A busca pelo nome da cidade é \emph{insensível a acentos}: utilizamos a extensão \texttt{unaccent} no filtro (\texttt{unaccent(lower(c.name)) = unaccent(lower(p\_city\_name))}), de modo que ``sao paulo'', ``São Paulo'' e ``SÃO PAULO'' retornam o mesmo resultado. Como consequência dessa escolha, o índice \texttt{idx\_cities\_country\_lower\_name\_coordinates} passa a ter papel secundário nesse filtro específico (a expressão indexada não corresponde mais exatamente ao predicado); ele continua útil para restringir cidades por país e por coordenadas disponíveis.

\subsection{Relatório 3 -- Admin: Relatório Hierárquico de Corridas}

O relatório 3 foi dividido em duas partes:

\begin{itemize}
    \item {\small\texttt{app\_admin\_relatorio\_3\_escuderias\_pilotos}}: lista todas as escuderias cadastradas e a quantidade de pilotos que correram por cada uma;
    \item {\small\texttt{app\_admin\_relatorio\_3\_hierarquico\_corridas}}: organiza as corridas em formato hierárquico.
\end{itemize}

A parte hierárquica foi organizada em três níveis:

\begin{enumerate}
    \item total de corridas cadastradas;
    \item estatísticas de corridas por circuito;
    \item detalhes das corridas de cada circuito.
\end{enumerate}

Para representar o relatório multinível em formato tabular, a função retorna uma coluna \texttt{nivel}. Assim, as linhas de nível 1 representam o total geral, as linhas de nível 2 representam o resumo por circuito e as linhas de nível 3 representam as corridas pertencentes a cada circuito.

\subsection{Relatório 4 -- Escuderia: Vitórias por Piloto}

Este relatório lista os pilotos que correram por uma escuderia e a quantidade de vezes em que cada piloto obteve primeira posição.

\subsection{Relatório 5 -- Escuderia: Resultados por Status}

Este relatório apresenta a quantidade de resultados por status, limitada ao escopo da escuderia logada.
\subsection{Relatório 6 -- Piloto: Pontos por Ano e Corridas}

Este relatório apresenta os pontos obtidos pelo piloto por ano de participação, indicando as corridas em que os pontos foram obtidos.

O total de pontos por ano é retornado como \texttt{NUMERIC(10,2)}, e não como inteiro. Isso porque a Fórmula 1 atribui meios-pontos em situações específicas (por exemplo, corridas encurtadas). Essa escolha mantém o relatório consistente com o \textit{dashboard} do piloto, que também trabalha com pontos fracionários.

\subsection{Relatório 7 -- Piloto: Status das Corridas}
Este relatório apresenta a quantidade de resultados por status nas corridas em que o piloto participou.

\section{Interface da Aplicação}

A interface foi desenvolvida em Streamlit (Python) e roda localmente, conectando-se ao PostgreSQL em execução no container Docker. Toda consulta feita pela aplicação chama, de forma explícita, uma \textit{view} ou função já criada no banco; não há lógica de negócio duplicada em Python nem uso de \textit{ORM}, o que mantém o SQL visível para avaliação.

A aplicação é centrada em três telas principais --- login, \textit{dashboard} e relatórios ---, cada uma com variações de acordo com o tipo de usuário autenticado. Após o login, a navegação entre as telas é feita por um menu na barra lateral, organizado em itens de texto clicáveis e adaptado ao perfil do usuário: o administrador acessa ``Visão Geral'', ``Cadastros'' e ``Relatórios''; a escuderia acessa ``Visão Geral'', ``Ações'' e ``Relatórios''; e o piloto, por ser somente leitura, acessa apenas ``Visão Geral'' e ``Relatórios''. A mesma barra lateral exibe a logo da Fórmula 1, o nome do usuário logado e o botão de \textit{logout}, disponível em qualquer tela.

\subsection{Tela de Login}

A tela inicial solicita login e senha e autentica o usuário pela função \texttt{app\_login}, que valida a senha protegida com \texttt{pgcrypto} e registra o evento de \texttt{LOGIN} na tabela \texttt{users\_log}. Em caso de credenciais inválidas, uma mensagem de erro é exibida; com a autenticação bem-sucedida, o usuário é direcionado à tela de \textit{dashboard}.

\section{Decisões de Projeto}

Esta seção reúne as principais escolhas do grupo e a justificativa de cada uma.

\subsection{Modelagem e tratamento de dados (Trabalho Prático T1)}

A modelagem do esquema e o tratamento/limpeza dos dados utilizados nesta aplicação são os disponibilizados no \emph{gabarito de referência} do Trabalho Prático T1. Optamos por reaproveitar essa versão de referência por ser a base já validada ao longo da disciplina, sobre a qual a aplicação foi construída.

\subsection{Escolha do Streamlit como tecnologia de interface}

Escolhemos o \textbf{Streamlit} (Python) por permitir construir as telas, formulários e, principalmente, os \textit{dashboards} de forma prática e rápida, com componentes prontos de tabela, métrica e gráfico, sem exigir um \textit{front-end} web separado. Assim, o esforço ficou concentrado no que o trabalho de fato avalia --- consultas, funções, views, índices e \textit{triggers} ---, enquanto a camada de interface apenas chama as views e funções já criadas no banco. Os gráficos dos \textit{dashboards} foram montados com Altair (já incluído no Streamlit), configurados de forma estática (sem zoom ou arraste) para priorizar a leitura clara dos dados.

\subsection{Autenticação pela tabela \texttt{users} com hash, em vez de usuários reais do SGBD}

O enunciado permite duas abordagens: usar usuários reais do PostgreSQL (com autenticação \texttt{SCRAM-SHA-256}) ou autenticar diretamente por uma tabela \texttt{users}, desde que a senha não seja armazenada em texto puro. Optamos pela segunda. Assim, não é necessário criar e gerenciar centenas de \textit{roles} reais no SGBD (uma por piloto e por escuderia), o protótipo fica mais portável entre máquinas e a lógica de login/logout pode ser controlada pela própria aplicação. As senhas são armazenadas como \textit{hash} gerado com \texttt{pgcrypto} (\texttt{crypt()} com \texttt{gen\_salt('bf')}, isto é, \textit{bcrypt}), nunca em texto puro.

\subsection{Lógica de negócio no banco e SQL explícito na aplicação}

Todas as operações da aplicação (consultas, cadastros, importação, login) são implementadas como \emph{views} e \emph{funções} no banco. A camada em Python apenas chama essas views/funções com SQL explícito, sem utilizar um ORM. Essa decisão concentra a regra de negócio em um único lugar (o banco), evitando duplicação de lógica entre SQL e Python.

\subsection{Tabela própria de vínculo entre escuderia e piloto}

Na base original, a associação entre piloto e escuderia só existe na tabela \texttt{results}, ou seja, apenas após participação real em corrida. Como a importação de pilotos por arquivo pode cadastrar pilotos que ainda não correram, criamos a tabela \texttt{app\_escuderia\_pilotos} para registrar esses vínculos. Ela é populada inicialmente com os pares distintos de \texttt{results}, recebe os vínculos criados na importação e é mantida atualizada por \textit{trigger} quando novos resultados surgem. A tabela aceita um mesmo piloto vinculado a mais de uma escuderia, preservando mudanças de equipe ao longo da carreira.

\subsection{Separação entre consultas de desempenho e consultas cadastrais}

Como consequência da decisão anterior, separamos dois tipos de consulta. As consultas de \emph{desempenho} (pontos, vitórias, temporadas, status) usam \texttt{results} ou \texttt{vw\_resultados\_corridas}, pois dependem de participação real em corrida. A \emph{consulta de piloto por sobrenome} também usa \texttt{results}, porque o enunciado pede pilotos que \emph{já correram} pela escuderia (e dá a dica de consultar \texttt{results}). Já a \emph{listagem} cadastral de pilotos vinculados usa \texttt{app\_escuderia\_pilotos}, pois aí faz sentido incluir também os pilotos recém contratados que ainda não têm resultados.

\subsection{Sincronização e consistência de usuários por \textit{triggers}}

Optamos por delegar a criação e a remoção dos usuários de piloto e escuderia a \textit{triggers} nas tabelas \texttt{drivers} e \texttt{constructors}, em vez de fazer isso no código da aplicação. Assim, qualquer inserção nessas tabelas --- venha da interface ou de um comando SQL direto --- gera o usuário correspondente automaticamente. Quando o \textit{login} gerado já existe para outro usuário, a \textit{trigger} cancela a operação com \texttt{RAISE EXCEPTION}, impedindo inserção inconsistente. Na prática, como \texttt{constructor\_ref} e \texttt{driver\_ref} são únicos, a restrição \texttt{UNIQUE} da tabela de origem costuma barrar o caso comum de referência repetida antes mesmo da \textit{trigger}; a verificação na \textit{trigger} garante o cancelamento também no cenário em que o \textit{login} já existe por outro caminho.

\subsection{Busca de cidade insensível a acentos (Relatório 2)}

Para melhorar a usabilidade, a busca de cidade do Relatório 2 ignora acentuação e caixa, usando a extensão \texttt{unaccent}. Dessa forma, ``sao paulo'' e ``São Paulo'' retornam o mesmo resultado. Como consequência, o índice de cidade deixa de casar exatamente com o predicado, passando a ter papel secundário nesse filtro.

\subsection{Pontuação com casas decimais (Relatório 6)}

O total de pontos por ano é tratado como \texttt{NUMERIC(10,2)}, e não como inteiro, porque a Fórmula 1 atribui meios-pontos em situações específicas. Truncar para inteiro perderia esses 0,5 ponto e tornaria o relatório inconsistente com o \textit{dashboard} do piloto.

\subsection{Controle de acesso por perfil}

Cada tipo de usuário enxerga apenas o que lhe cabe. As funções de escuderia e de piloto recebem o \texttt{id\_original} do usuário logado e filtram os dados por esse identificador. Na interface, o menu lateral exibe apenas as páginas e ações do perfil autenticado, e o usuário do tipo \texttt{Piloto} é somente leitura, sem qualquer ação de cadastro, conforme o enunciado.

\subsection{Importação de pilotos por \textit{upload} de arquivo}

Optamos por implementar a importação como \textit{upload} pelo navegador (\textit{widget} de envio de arquivo do Streamlit), o que é mais prático de demonstrar e não depende de o arquivo estar em um caminho específico do servidor. O arquivo é carregado em uma tabela de \textit{staging} e processado pela função \texttt{app\_escuderia\_processar\_importacao\_pilotos}, que rejeita linhas cujo nome e sobrenome já existam em outro piloto.

\subsection{Organização da carga em dois \textit{scripts}}

A carga foi separada em \texttt{load\_database.sh} (esquema, dados e limpeza) e \texttt{load\_app.sh} (usuários, ações, índices, views, dashboards e relatórios). Isso permite recarregar apenas a camada da aplicação durante o desenvolvimento, sem reprocessar toda a base a cada alteração em uma função, view ou índice.

\section{Dificuldades Encontradas}

De modo geral, o projeto não apresentou grandes dificuldades. As atividades realizadas ao longo do semestre foram muito úteis e puderam ser aproveitadas diretamente no trabalho final: várias das consultas, assim como agregações, filtros, criação de funções, \textit{views} e \textit{triggers}, além do cálculo de distância geográfica já haviam sido exercitadas em atividades anteriores. Isso reduziu bastante o esforço com as buscas do projeto, pois boa parte do raciocínio (e até de trechos de consulta) pôde ser reaproveitada.

Ainda assim, alguns pontos exigiram mais atenção, como costuma ocorrer em projetos desse tipo:

\begin{itemize}
    \item integração de bases heterogêneas (Fórmula 1, países, cidades e aeroportos), que exige cuidado com chaves, vínculos e padronização de nomes;
    \item garantir que cada perfil de usuário acesse apenas as informações que lhe são permitidas;
    \item ajustes de ambiente e configuração (Docker e conexão com o banco) para que o projeto rodasse de forma reprodutível entre os integrantes do grupo.
\end{itemize}

Esses pontos foram tratados de forma incremental e, por já terem sido abordados de alguma maneira durante a disciplina, foram mais traquilos de resolver nesse momento. 
\section{Conclusão}

O trabalho atingiu o objetivo proposto: desenvolver um protótipo de aplicação completa para exploração da base de dados da Fórmula 1, integrada a dados geográficos de países, cidades e aeroportos. A ferramenta autentica três perfis de usuário (administrador, escuderia e piloto), apresenta \textit{dashboards} personalizados, executa os relatórios solicitados e oferece as ações de cadastro, consulta e importação previstas no enunciado, sempre respeitando as permissões de cada perfil.

Do ponto de vista de banco de dados, o projeto reuniu os principais conceitos estudados na disciplina: criação e normalização do esquema, limpeza e deduplicação dos dados, consultas com junções, agregações e filtros, \textit{views} reutilizáveis, funções e procedimentos armazenados, \textit{triggers} para manter a consistência entre as tabelas, índices para apoiar as consultas mais frequentes e um modelo de autenticação com senhas protegidas. A opção por concentrar a lógica no banco e manter o SQL explícito na aplicação reforçou esses conceitos.

A integração entre os recursos do PostgreSQL e a interface em Streamlit mostrou-se eficaz para transformar consultas em informações organizadas e de fácil leitura para o usuário final. Como evolução futura, o projeto poderia incluir novos relatórios e filtros, gráficos comparativos entre temporadas, atualização da base com as corridas mais recentes e refinamentos adicionais na deduplicação de cidades feitas manualmente.
